# Saudi SME Scorecard — Data Dictionary

**Generated from the live catalogue** by `scripts/generate_sme_data_dictionary.py`. Do not hand-edit: a data dictionary that disagrees with the data is worse than no data dictionary, because it is believed.

Catalogue version `1.0.0` · variables version `1.0.0` · domain **Saudi SME Scorecard** · owner Model Risk & Validation

---

## 1. What this data is, said plainly

Every row in every dataset here is **synthetic**. It was generated by `backend/scorecard/sme/synthetic.py` from a seeded random number generator. No row describes a real business, a real applicant, a real facility or a real default.

Of the 90 variables in the SME universe, **26 are proxies** for data that a real Saudi deployment would source from an external authority. They carry names ending `_proxy` and a source family ending `_PROXY`, and they are marked ⚠ in §4.

The champion scorecard itself is fitted on **8** of those variables (§5). The remainder are carried because a validation needs more than the characteristics that were selected: a variable rejected at development is exactly what `VAR-*` has to look at when the selected ones weaken.

The distinction matters more than any other statement in this document, so it is made once without hedging:

> **CreditProbe is not connected to SIMAH, ZATCA, FATOORA, GOSI, Qiwa, Mudad, Monsha'at, the Ministry of Commerce, a credit bureau, or any core banking system.** The variables below are shaped like what those sources return, so that the validation machinery can be exercised against realistic distributions. They are not those sources, and a demonstration that describes them as a live feed is making a false statement about the product.

The generator is seeded through a BLAKE2b digest rather than Python's `hash()`, so the universe is identical in every process and on every machine. That is a validation requirement, not a convenience: two validators computing the same AUC must get the same number.

## 2. Datasets

### `sme_scorecard_monthly_validation`

**SME Scorecard Monthly Validation** · One row per application. · 57 fields

One row per SME application per cohort, scored by the champion and the challenger, with the realised twelve-month outcome where the performance window has closed.

### `sme_scorecard_development_reference`

**SME Scorecard Development Reference** · One row per development-window application. · 57 fields

The out-of-time population the approved binning was fitted on, and the calibration with it. The default baseline for every stability comparison.

### `sme_scorecard_decisions`

**SME Scorecard Decisions and Overrides** · One row per application decision. · 21 fields

What was actually decided: the score, the grade, the decision, whether it was overridden and why, and how the overridden cases performed. A narrow view on purpose — a decision file that repeats every predictor invites somebody to answer a model question from it.

**Relationships**

| From | To | Kind | On | Why |
|---|---|---|---|---|
| `sme_scorecard_monthly_validation` | `sme_scorecard_development_reference` | BASELINE_COMPARISON | `cohort_month` | Stability is measured against the development population. |
| `sme_scorecard_decisions` | `sme_scorecard_monthly_validation` | ONE_TO_ONE | `cohort_month`, `application_id` | The decision taken on a scored application. |

The baseline relationship is the one the stability tests depend on. `sme_scorecard_development_reference` is the frozen out-of-time population the approved binning was fitted on; every PSI and CSI in the module is measured against it rather than against last month. Drifting the baseline forward is how a scorecard passes stability testing for three years while moving a long way from what was approved.

## 4. Scorecard variables

## 5. The champion model as the registry holds it

| Property | Value |
|---|---|
| Model ID | `sme_champion` |
| Name | Saudi SME Scorecard |
| Domain | `scorecard_saudi_sme` |
| Score column | `champion_score` |
| Score direction | `HIGHER_SCORE_IS_BETTER` |
| PD column | `champion_pd_12m` |
| Outcome column | `actual_default_12m` |
| Maturity flag | `is_matured` |
| Default definition | 90 days past due or worse, or a credit-impaired restructuring, within twelve months of the score date. |
| Performance window | 12 months |
| Observation window | Monthly application cohort |
| Development population | 2022-01..2022-12 |
| Score range | 300–900 |
| Cut-off | 600 |
| Scaling | base score 600 at odds 30:1, 40 points to double the odds |
| Reference | MDL-SME-KSA-001 v1.0.0 (challenger 1.1.0-C) |
| Tier / materiality | TIER_1 / HIGH |
| Binned variables | 8 |
| Configured limits | 15 |
| Segmentation fields | `enterprise_size_class_proxy`, `economic_sector`, `region` |

`score_direction` is stated explicitly rather than inferred. A scorecard where a high score means a good customer and one where a high score means a bad one produce AUCs that are reflections of each other, and a module that guesses will eventually report 0.35 as a failure when the model is fine and the reader is holding it upside down.

**Known limitations recorded at approval**

- Every input is generated. CreditProbe is not connected to a commercial bureau, a tax authority, an e-invoicing platform, a social-insurance register or a bank core system, and each field standing in for one of those carries `_proxy` in its name.
- The score-to-PD calibration was fitted on the development sample and has not been refitted since.

## 6. Where the numbers in a report come from

Every statistic computed on this data goes through `backend/scorecard/metrics.py` or `backend/scorecard/binning.py`. Nothing in the validation package computes a statistic itself, and no language model computes one at all. See `docs/SCORECARD_VALIDATION_ARCHITECTURE.md` §5.
