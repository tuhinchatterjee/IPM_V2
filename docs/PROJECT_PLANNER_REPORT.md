## A. What was built

A delivery planning capability inside CreditProbe, reusing its authentication,
users, teams, permission model, notification centre, audit table, durable job
queue, agentic tool registry, design system and test architecture. It
introduces no second user table, no second notification table, no second audit
table and no scheduler of its own.

Ten tables (`planner_*`), one migration, six backend modules, twenty-eight
routes, three screens, twelve registered AI tools, a nine-sheet workbook in
both directions, an overnight sweep, a seeded plan and 112 backend tests.

The naming collision was real and resolved deliberately: `projects` already
exists as the analytical workspace a piece of credit work lives in. These are
the projects a team *delivers*, they live in `planner_*` tables at `/delivery`,
and the navigation entry says which is which.

## B. The user experience

Three routes under `/delivery`.

**Portfolio.** Stat cards, an Attention panel above the fold with the reason
written out for each project, and a table led by health and lateness rather
than by name — the reader has four questions in that order. Search and health
and status filters, debounced.

**My work.** Six buckets, each task in exactly one, ordered by what needs the
person first. A task that is overdue AND blocked appears once, under Blocked,
because listing it twice makes nine items look like eleven.

**Project detail.** Seven tabs in the order somebody asks: Overview, Plan,
Milestones, RAID, People, Updates, Brief. The header carries health with its
reason, progress, and how long since anybody said anything.

Decisions worth stating:

* health is a colour **and** the word. A status report gets printed,
  photocopied, and read by people who cannot distinguish the greens;
* a manually reported health shows the calculated one beside it. Somebody
  deciding a project is greener than its own numbers is a governance fact;
* the quick update carries status, progress, a sentence and blocked-with-a-
  reason — **not** the owner and not the date. Moving the date you are
  measured against is a change to a commitment, the backend refuses it from a
  contributor, and a field that only ever produces a 403 is worse than no
  field. The drawer says so in a line rather than leaving it to be discovered;
* every save sends the version it read, and a 409 reads as "somebody got there
  first", not as a red validation error.

## C. The agentic behaviour

Twelve tools in the existing registry; eleven read. Every read tool is marked
`reads_data`, which is what carries the requesting person's principal into the
handler — an agent answering "what's overdue?" sees exactly what that person
could see by clicking.

**There is no registered tool that completes a task, changes an owner, moves a
due date, cancels work, closes a risk or sets a project's health.** Those six
names are in `NO_TOOL_EXISTS` beside the platform's other prohibited actions.
The prohibition is the absence of the capability, not a permission check that
has to be written correctly. The single writer drafts the text of a status
request and sends nothing.

Briefs are composed from the deterministic engine, not generated. Every line
is labelled FACT, INFERENCE, RECOMMENDATION or NOT RECORDED. Where a task is
blocked with no reason recorded, the brief says exactly that and puts the
question in `open_questions` rather than offering a plausible sentence about a
vendor.

## D. The database

Ten tables, migration `0034`, single head, upgrade and downgrade both
verified. 34 indexes, 38 foreign keys, 8 unique constraints — scoped correctly
(task codes unique *within a project*, not globally; one reminder per
fingerprint; one participant per person per project).

The autogenerated migration also proposed a dozen unrelated alterations where
the live schema has drifted from the models elsewhere — type widenings and
index drops on `agent_runs`, `analysis_runs`, `investigations`,
`review_queue_items`, `risk_cases` and the workflow tables. Every one was
removed and the removal recorded in the migration's docstring. They are real
and they are somebody else's change to make deliberately; carrying them here
would mean a migration named "project planner" quietly dropping an index on
`analysis_runs`.

## E. Services and APIs

Every mutation does the same five things in the same order: resolve access,
validate, apply and bump the version, append an immutable history row, write a
`collaboration_audit` record naming the actor and the SOURCE. Nothing in the
service layer commits — the caller owns the transaction, which is what makes a
four-hundred-row Excel import atomic.

Twenty-eight routes. `ProjectNotFound` → 404, `ProjectDenied` → 403,
`StaleWrite` → 409, `PlannerError` → 422 with the sentence the service wrote.
No stack trace reaches a user.

## F. The workbook

One column contract drives the template, the export and the parser, so
export → edit → import is a round trip rather than two formats that resemble
each other. Nine sheets: an IMPORT GUIDE plus PROJECT, PARTICIPANTS,
WORKSTREAMS, TASKS, MILESTONES, DEPENDENCIES, RAID, UPDATES.

* **Omission is not deletion** — and the guide sheet says so inside the file.
* **Nothing is applied from a file nobody has seen** — upload stages, commit
  applies the staged copy.
* **Columns are matched by header, never by position.**
* **Cells are data, never formulas** — and the escape survives the round trip.
* The UPDATES Author column is filled in on export and ignored on import.

## G. Security

The access boundary is the participant list (CreditProbe is single-tenant;
there is no organisation table). Two properties are enforced and tested:

* a project you are not on returns **404, not 403** — 403 confirms existence
  and turns `/projects/{id}` into a way to count the estate;
* a contributor may report progress but not move a due date.

Thirty-two adversarial tests, the interesting half of which are not "read
somebody else's project" but "make my project point at a row in theirs" —
which is why Mallory has a project of her own. Cross-project dependencies,
parents and RAID links are all refused by name. Hostile identifiers (`0`,
`-1`, `1 OR 1=1`, `../1`, `1;DROP TABLE planner_tasks`) return 404 or 422 with
no traceback, and a following test confirms the tables are still there.

Two deliberate asymmetries, both tested in both directions:

* **titles are not sanitised.** A risk genuinely called `<Finance> won't sign
  off` must survive; the defence belongs where the danger is — escaping into a
  spreadsheet, React escaping into the page — not in a blocklist that mangles
  honest text. Codes *are* constrained, because they become filenames and
  cells;
* **a workbook is judged on its magic bytes, not its Content-Type.** The label
  is the caller's claim, and refusing a genuine workbook called `plan.pdf`
  would be a support ticket a week.

Some attacks fail because there is nothing to attack: no route deletes a
project, no route edits history, and no registered tool changes a commitment.

## I. Browser acceptance

Six journeys and forty-three checks, driven through a real Chromium against a
real backend, signed in as `priya.raman` through the actual login form rather
than with `REQUIRE_LOGIN=false`. My Work shows what *you* own, and that only means
something as a named person; an administrator sees everything and therefore
proves nothing about that screen.

Each journey asserts something a screenshot cannot: that the stat card's red
count equals the red rows behind it, that the health reason on the project page
is the same sentence as on the portfolio, that the brief agrees with the header
about the colour, that a saved update closes the drawer, and that an export is
refused without a session.

The two `/delivery` list routes were also added to the existing four-viewport,
four-theme crawl in `scripts/browser_acceptance.py`.

## J. What the reviews found

Nine of the defects below were found by tests I wrote against my own code.
That is the point of writing them.

1. **`verdict.health` on a dataclass whose field is `status`** — the overnight
   sweep would have crashed on every run. Found by the monitor suite.
2. **The workbook addressed dependencies as `from_type`/`to_type`** against a
   model whose columns are `predecessor_`/`successor_`. Exporting any project
   with a dependency raised `AttributeError`, and no test caught it because the
   workbook fixtures had no links in them. Found by the seed.
3. **The RAID sheet exported a `due_date` column** against a model whose field
   is `target_date`, so every risk's date round-tripped as empty. Found by the
   AI suite.
4. **Nine frontend/backend shape mismatches** that TypeScript asserted and the
   backend did not send — including `access.level`, which crashed the project
   page outright, and `totals.red`, which made both stat cards read 0 next to a
   table with a red row in it. Found by the browser journeys.
5. **An unchanged export re-imported reported every participant and dependency
   as a creation** — their handlers had no notion of what already existed.
6. **A weight stored as `Decimal("1.00")` compared as text against an exported
   `1.0`** called every untouched row an update.
7. **`create_raid` stored `linked_entity_id` unchecked**, so a risk on my
   project could carry the id of a task on yours. Found by the adversarial
   suite.
8. **`my_work(horizon_days=...)` did nothing** — both branches that consulted
   it appended to the same bucket. Removed from the service, the route, the
   tool registry and the API client. Found by the second-engineer read.
9. **The seed backdated its history but not the tasks' own
   `last_update_at`**, so the plan's story said a task had been silent for
   five days while the task claimed it had just been updated — and the chase
   list came out empty. A plan that looks healthier than the story it tells.
   Found by a browser check that asserted somebody owed an update.
10. **The health engine double-counted** a task that was both overdue and
   stale, and **claimed a task at 90% had "never been updated"**. Both fixed in
   the engine before the API existed.

## K. Remaining limitations

Stated, not hidden.

* **The critical path is a marker, not a computed longest path.** Tasks carry
  a `critical` flag and dependencies are real and cycle-checked, but the engine
  does not compute float or a CPM schedule. `control.py` refuses to claim
  otherwise: it reports what is blocking what and what is late, and never
  presents a critical path it has not calculated.
* **No Gantt or timeline renderer.** The Plan tab is a list with dependencies
  below it. Its absence is visible rather than faked.
* **RAID and milestones can be created and read on screen, not edited there.**
  Raising a risk and adding a milestone both have forms on the project page;
  changing an existing one (closing a risk, marking a milestone achieved) is
  still API-and-workbook only.
* **The sweep is registered but not scheduled.** The job kind is wired into the
  existing worker and can be run by hand or enqueued; deciding when it fires is
  a deployment choice, and nothing fires it automatically today.
* **Reminders are in-app only**, following the platform's existing decision.
* **No AI wording of chases, and nothing sends them.** The deterministic rules
  choose who to chase and why; the draft is composed from those rules and shown
  on the project page with a Copy button. A model could word it more warmly;
  nothing calls one today. Nothing is sent from the product — the response says
  `"sent": false` and the panel says so on screen.
* **Docker is NOT VERIFIED IN CLAUDE SANDBOX.** Everything above was run
  against a local PostgreSQL, a local uvicorn and a local `next start`.
